# Editable local domains and scoped system integration

The user selected `.test` as the default suffix and requires editable full domains. Router settings therefore contain explicit per-project hostnames. Strict DNS hostname validation rejects configuration injection, paths, wildcards and IP addresses; international hostnames can use their ASCII punycode form. Custom names can overlap public names, so the system change preview explains the local DNS effect.

Caddy binds only loopback on explicitly selected unprivileged ports. Generated configuration disables the admin endpoint, config autosave, automatic HTTP redirects and automatic trust installation. HTTPS uses a private internal CA with storage in the private Dockon data directory. This follows the documented [Caddy global options](https://caddyserver.com/docs/caddyfile/options), [loopback binding](https://caddyserver.com/docs/caddyfile/directives/bind) and [internal TLS issuer](https://caddyserver.com/docs/caddyfile/directives/tls).

A router plan validates the generated configuration before returning a one-use five-minute approval token and before/after text. Applying verifies that project state has not changed and stages another validation before restarting the shared router. Startup failure attempts to restore the previous configuration. Runtime installation changes and router changes never switch project runtimes. Lifecycle observation replaces stopped upstream routes with 503 responses; project processes remain independently owned. Saved settings do not autostart the router after daemon restart.

Hosts and CA trust have separate previews and one-use approval tokens. The hosts helper accepts only bounded structured domain changes, verifies the reviewed plan digest and existing hosts digest, rejects conflicting mappings and symlinked hosts files, locks the fixed OS hosts file, backs it up and replaces only this installation's marked block. It accepts no target path or shell command. Windows uses a hidden scoped helper through the [ShellExecuteEx runas permission flow](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecuteexw); macOS uses its administrator dialog; Linux requires pkexec. Live elevation has not been exercised on the development host.

Windows CA trust uses the native current-user ROOT store APIs ([CertOpenStore](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certopenstore), [CertAddEncodedCertificateToStore](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certaddencodedcertificatetostore)). The preview shows the exact DER certificate's SHA-256 digest. Removal compares complete DER bytes before deleting the matching certificate. No machine-wide trust store is modified. Trust mutation has not been run on the development host; Linux/macOS automated trust is explicitly unsupported pending platform adapters. Independent browser trust stores are not silently edited.

Router tests use their own CA in a test HTTP client, verify that an unconfigured client rejects it, check permission previews and reject forged tokens. Hosts write/backup tests operate on temporary fixture files; integration checks verify the real system hosts file remains unchanged. These checks do not establish that OS permission dialogs or browser trust integration have been verified.

Native Windows certificate add/find/remove behavior is also tested in a disposable in-memory store with a public certificate fixture. Those tests do not open the real ROOT store. Caddy release discovery uses the publisher's direct latest-release redirect and checksum download, avoiding the shared unauthenticated GitHub API quota hit by the first macOS CI router run.
